# Benchmarks

Measured on 2026-11-24 on a 2-vCPU machine. All numbers below come from the
commands in [Reproducing](#reproducing). Nothing is extrapolated.

## Summary

The tools compared are `gzip` 1.12 and `zstd` 1.5.5. Unless a line says
otherwise, every speed comparison is like-for-like on **one core**: pcz with
`-workers 1`, `gzip` (single-threaded), and `zstd -T1`. Decompression is
single-threaded in gzip and zstd. The pcz rows quoted are `-sched steal`;
with one worker the scheduler is not used, and `-sched static` is within 3%.

**One core: pcz vs gzip -1 vs zstd -1 -T1** (256 MiB each, median of 3)

| dataset | ratio: pcz / gzip -1 / zstd -1 | compress MB/s: pcz / gzip -1 / zstd -1 | decompress MB/s: pcz / gzip -d / zstd -d |
|---|---|---|---|
| text | 1.566 / 2.179 / 2.444 | 146 / 48 / 177 | 204 / 109 / 497 |
| logs | 3.735 / 5.118 / 6.108 | 238 / 101 / 330 | 391 / 186 / 665 |
| mixed | 1.697 / 2.074 / 2.225 | 210 / 50 / 270 | 296 / 136 / 709 |

- **zstd -1 beats pcz on every dataset on ratio, compression speed and
  decompression speed.** On one core zstd compresses 1.2–1.4× faster and
  decompresses 1.7–2.4× faster, and pcz's output is 31–64% larger than
  zstd's.
- **Against gzip -1, pcz compresses 2.4–4.2× faster and decompresses
  1.9–2.2× faster, but its output is 22–39% larger.**
- pcz has the lowest ratio of all the tools on all three datasets. Its codec
  is LZ4-style with no entropy coding, so this is expected.
- **pcz on 2 cores vs single-threaded gzip:** compression is 4.3–7.5×
  faster than `gzip -1` and decompression 3.3–3.6× faster than `gzip -d`.
  This is not like-for-like. pigz (parallel gzip) was not installed, so
  multi-core gzip was not measured.
- **pcz on 2 cores vs zstd on 2 cores (`-T0`):** zstd compresses faster on
  all three datasets (309 vs 271, 530 vs 436, 444 vs 377 MB/s). zstd
  decompression on one core is still faster than pcz on two for `text`
  (497 vs 363) and `mixed` (709 vs 486), and about equal for `logs`
  (665 vs 650, overlapping ranges).
- **Scaling 1 → 2 workers:** pcz compression gains 1.79–1.86× and
  decompression 1.64–1.78×. `zstd -T0` gains 1.61–1.74× over `-T1` on
  compression.
- **Scheduler:** with 2 workers, `static`, `steal` (Chase–Lev work
  stealing) and a plain atomic-counter baseline perform within a few
  percent of each other. Work stealing shows no measurable benefit here; in
  the in-process benchmark its median is the slowest of the three (about 5%
  below static).
- **Scaling beyond 2 cores was not measured on this machine.** Nothing here
  says how pcz behaves on 4, 8 or more cores.

The t4g family is burstable. Before the final runs, a sustained 25-run
single-worker probe and a 40-run two-worker probe held steady (±3%), so the
runs showed no sign of throttling (CPU credit balance not checked). Earlier
exploratory runs in the same session did show a transient slowdown from
outside load. They were discarded, and the final runs were made with the
machine otherwise idle (load average 0.2–0.8 before each run). Every table
shows min and max so the spread is visible.

## Definitions

- **MB/s** = (uncompressed input bytes / 10^6) / wall-clock seconds. The same
  formula is used for decompression: it is the rate of producing the
  original bytes.
- **Ratio** = uncompressed bytes / compressed bytes. Higher is better.
- Each cell is the **median of 3** runs, with **(min–max)** in parentheses.

## Datasets

Generated by `cmd/gendata` with seed 1, 256 MiB (268,435,456 bytes) each.
The data is synthetic, so these ratios show how the tools compare on these
shapes of data, not what you will get on your own files.

| name | content | SHA-256 (with go1.27.4) |
|---|---|---|
| `text` | English-like prose: a Zipf-distributed vocabulary of 20,000 words (the 49 most frequent are real English function words, the rest are generated syllable words), in sentences and paragraphs | `67504fde8d73c2f03f74ab66b16b3f9feda997bf4304eb1c67574202f9f9f4d4` |
| `logs` | JSON log lines with fixed keys (`ts`, `level`, `service`, `msg`, `method`, `path`, `status`, `latency_ms`, `user_id`, `request_id`) and varying values | `939fde491e500e7647adc2463eaf57307ff724ef56c13260135cad7a2371b234` |
| `mixed` | 256 KiB segments in groups of five: 1 random, 3 `text`, 1 zeros, shuffled per group (20% / 60% / 20%) | `ce09c2ed81a3c224826a15ec39d8c91624ce0f35fdd8589308f28e3ddcc413a2` |

The hashes depend on Go's `math/rand/v2` generators. They were produced
with go1.27.4; another Go version could in principle give different bytes.

## CLI results (`scripts/bench.sh`)

Every tool reads the input file on stdin and writes stdout to a file on
disk (`$BENCH_DIR`). Inputs are in the page cache. Outputs are deleted
between runs. After every timed run the result was checked with `cmp`
against the original (compressed outputs are first decompressed, untimed),
and every pczip configuration produced byte-identical compressed output.
pczip uses its default 1 MiB block size. Decompression was timed for
`-sched steal` with 1 worker and with 2 workers; the `static` rows were
verified but their decompression was not timed. `zstd -1 -T1` is not in the
original task brief; it is the single-core comparison for
`pczip -workers 1`.

## In-process results (`go test -bench`)

`pcz/bench_test.go` runs `Compress` and `Decompress` on 32 MiB of `mixed`
(seed 1) held in memory, so there is no file or pipe I/O. MB/s is from
`b.SetBytes` (uncompressed bytes). `atomic-counter` is a baseline scheduler
defined only in the test file: workers claim the next block index from one
shared atomic counter. Its compressor is a copy of `Compress` with only the
scheduler call swapped, and a test checks that its output is byte-identical.

**Table: in-process MB/s, 2-vCPU machine; the workers column is the number
of cores used.** Five runs (`-count=5`) of 3 iterations each; median
(min–max) of the five.

| benchmark | workers (cores) | static | steal | atomic-counter |
|---|---|---|---|---|
| Compress | 1 | 219 (205–222) | 214 (211–219) | 217 (210–221) |
| Compress | 2 | 396 (388–409) | 376 (368–390) | 393 (391–398) |
| Decompress | 1 | 309 (279–311) | 307 (306–314) | – |
| Decompress | 2 | 562 (482–585) | 548 (519–563) | – |

Compression ratio on this input: 1.708. With 1 worker all three schedulers
run the blocks inline on the calling goroutine, so the 1-worker rows measure
the same code path. In-process decompression is faster than the CLI figures,
likely because it has no pipe or file I/O (not measured separately; the
input sizes also differ: 32 MiB here, 256 MiB in the CLI runs).

On 2 cores with blocks of similar cost, work stealing does not beat static
partitioning or the atomic counter. Stealing is designed to help when block
costs are uneven or there are many workers; neither case was measured here.

## Where pcz wins and loses (this machine, these datasets)

pcz figures are from the `-sched steal` rows (the only pcz rows with timed
decompression). Values are text / logs / mixed.

**Like-for-like, 1 core each** (pcz `-workers 1`, gzip, `zstd -T1`, and
single-threaded decompression):

| comparison | result |
|---|---|
| ratio vs gzip -1 | pcz loses on all three: 1.566 vs 2.179, 3.735 vs 5.118, 1.697 vs 2.074 |
| ratio vs zstd -1 | pcz loses on all three: 1.566 vs 2.444, 3.735 vs 6.108, 1.697 vs 2.225 |
| compress speed vs gzip -1 | pcz wins on all three: 146 vs 48, 238 vs 101, 210 vs 50 MB/s (2.4–4.2×) |
| compress speed vs zstd -1 -T1 | pcz loses on all three: 146 vs 177, 238 vs 330, 210 vs 270 MB/s |
| decompress speed vs gzip -d | pcz wins on all three: 204 vs 109, 391 vs 186, 296 vs 136 MB/s (1.9–2.2×) |
| decompress speed vs zstd -d | pcz loses on all three: 204 vs 497, 391 vs 665, 296 vs 709 MB/s |

**pcz on 2 cores** (`-workers 2`):

|---|---|

## Reproducing

```
export BENCH_DIR=$HOME/bench-data   # a disk directory with ~2 GB free
go test -run='^$' -bench=. -benchtime=3x -count=5 ./pcz/
bash scripts/bench.sh
rm -rf "$BENCH_DIR"
```

`scripts/bench.sh` builds `pczip` and `gendata` into `$BENCH_DIR/bin`,
generates the three datasets (`BENCH_SIZE`, default `256MiB`), and runs each
measurement `BENCH_RUNS` times (default 3). It skips gzip or zstd if not
installed. It prints the results table and the raw times. It stops with a
non-zero exit at the first tool that fails or the first `cmp` mismatch.
Regenerated datasets should match the SHA-256 values above when built with
the same Go version.

The task brief's `go test -run=^$ -bench=. -benchtime=3x ./pcz/` (one run)
also works; `-count=5` was used here to show spread.
