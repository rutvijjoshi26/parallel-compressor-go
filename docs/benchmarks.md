# Benchmarks

Measured on 2026-11-24. All numbers below come from the commands in
[Reproducing](#reproducing). Nothing is extrapolated.

## Summary

On this 2-core machine, against `gzip` 1.12 and `zstd` 1.5.5:

- **zstd -1 beats pcz on every dataset in compression ratio and compression
  speed**, both single-threaded (`zstd -T1` vs `pczip -workers 1`) and on
  2 cores (`zstd -T0` vs `pczip -workers 2`). zstd also decompresses faster
  on `text` and `mixed`. On `logs` the two decompress at about the same speed
  (663 vs 673 MB/s, overlapping min–max ranges).
- **pcz compresses 4–8× faster than `gzip -1`** and decompresses 3–4× faster
  than `gzip -d`, but its output is 22–39% larger than `gzip -1` output.
- pcz's ratio is the lowest of all tools tested on all three datasets. Its
  codec is LZ4-style (no entropy coding), so this is expected.
- Going from 1 to 2 workers speeds pcz compression up by 1.77–1.88×.
  `zstd -T0` gains 1.59–1.75× over `-T1` on the same machine.
- **Scheduler:** with 2 workers, `static`, `steal` (Chase–Lev work stealing)
  and a plain atomic-counter baseline perform within a few percent of each
  other. Work stealing shows no measurable benefit here; in the in-process
  benchmark its median is the slowest of the three (about 5% below static).
- **Scaling beyond 2 cores was not measured on this machine.** Nothing here
  says how pcz behaves on 4, 8 or more cores.

## Definitions

- **MB/s** = (uncompressed input bytes / 10^6) / wall-clock seconds. The same
  formula is used for decompression: it is the rate of producing the
  original bytes.
- **Ratio** = uncompressed bytes / compressed bytes. Higher is better.
- Each cell is the **median of 3** runs, with **(min–max)** in parentheses.

## Datasets

Generated by `cmd/gendata` with seed 1, 256 MiB (268,435,456 bytes) each.
The data is synthetic, so these ratios show how the tools compare on these
shapes of data, not what you will get on your own files.

| name | content | SHA-256 |
|---|---|---|
| `text` | English-like prose: a Zipf-distributed vocabulary of 20,000 words (the 49 most frequent are real English function words, the rest are generated syllable words), in sentences and paragraphs | `67504fde8d73c2f03f74ab66b16b3f9feda997bf4304eb1c67574202f9f9f4d4` |

## CLI results (`scripts/bench.sh`)

Every tool reads the input file on stdin and writes stdout to a file on
disk (`$BENCH_DIR`). Inputs are in the page cache. Outputs are deleted
between runs. Each round trip was checked with `cmp`, and every pczip
configuration produced byte-identical compressed output. pczip uses its
default 1 MiB block size. Decompression was timed for one pczip
configuration (`-sched steal -workers 2`); the other pczip configurations
were decompressed once, untimed, for the `cmp` check. `zstd -1 -T1` is not
in the task brief; it was added as the single-threaded comparison for
`pczip -workers 1`. "max" workers is 2 on this machine.

## In-process results (`go test -bench`)

`pcz/bench_test.go` runs `Compress` and `Decompress` on 32 MiB of `mixed`
(seed 1) held in memory, so there is no file or pipe I/O. MB/s is from
`b.SetBytes` (uncompressed bytes). `atomic-counter` is a baseline scheduler
defined only in the test file: workers claim the next block index from one
shared atomic counter. Its compressor is a copy of `Compress` with only the
scheduler call swapped, and a test checks that its output is byte-identical.

Five runs (`-count=5`) of 3 iterations each; median (min–max) of the five:

| benchmark | workers | static | steal | atomic-counter |
|---|---|---|---|---|
| Compress | 1 | 219 (205–222) | 214 (211–219) | 217 (210–221) |
| Compress | 2 | 396 (388–409) | 376 (368–390) | 393 (391–398) |
| Decompress | 1 | 309 (279–311) | 307 (306–314) | – |
| Decompress | 2 | 562 (482–585) | 548 (519–563) | – |

Compression ratio on this input: 1.708. With 1 worker all three schedulers
run the blocks inline on the calling goroutine, so the 1-worker rows measure
the same code path.

On 2 cores with blocks of similar cost, work stealing does not beat static
partitioning or the atomic counter. Stealing is designed to help when block
costs are uneven or there are many workers; neither case was measured here.

## Where pcz wins and loses (this machine, these datasets)

| comparison | result |
|---|---|
| ratio vs gzip -1 | pcz loses on all three: 1.566 vs 2.179 (text), 3.735 vs 5.118 (logs), 1.697 vs 2.074 (mixed) |
| ratio vs zstd -1 | pcz loses on all three: 1.566 vs 2.444, 3.735 vs 6.108, 1.697 vs 2.225 |
| compress speed vs gzip -1 (pcz 2 workers) | pcz wins on all three: 273 vs 48, 426 vs 101, 379 vs 50 MB/s |
| compress speed vs zstd -1 -T0 (2 cores) | pcz loses on all three: 273 vs 309, 426 vs 516, 379 vs 444 MB/s |
| compress speed vs zstd -1 -T1 (1 core) | pcz loses on all three: 145 vs 177, 239 vs 324, 214 vs 271 MB/s |
| decompress speed vs gzip -d | pcz wins on all three: 369 vs 109, 663 vs 169, 471 vs 137 MB/s |
| decompress speed vs zstd -d | pcz loses on text (369 vs 500) and mixed (471 vs 705); about equal on logs (663 vs 673, ranges overlap) |

## Reproducing

```
export BENCH_DIR=$HOME/bench-data   # a disk directory with ~2 GB free
go test -run='^$' -bench=. -benchtime=3x -count=5 ./pcz/
bash scripts/bench.sh
rm -rf "$BENCH_DIR"
```

`scripts/bench.sh` builds `pczip` and `gendata` into `$BENCH_DIR/bin`,
generates the three datasets (`BENCH_SIZE`, default `256MiB`), and runs each
measurement `BENCH_RUNS` times (default 3). It skips gzip or zstd if not
installed. It prints the results table and the raw times, and exits non-zero
if any round trip fails `cmp`. Regenerated datasets should match the SHA-256
values above.

The task brief's `go test -run=^$ -bench=. -benchtime=3x ./pcz/` (one run)
also works; `-count=5` was used here to show spread.
